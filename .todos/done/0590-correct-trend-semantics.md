# Correct Trend State Machine Semantics

- **ID:** 0590
- **Status:** done
- **Created:** 2026-09-23
- **Priority:** high
- **Depends:** 0589

## Problem

`compute_trend()` has two logic bugs. (a) The `n30 == 0` guard fires before the reversal check, so the first POSITIVE event after a negative streak is classified NEW instead of REVERSING — the most important signal case is misclassified. (b) FADING is applied to a currently-observed event that last appeared 31–90 days ago. But FADING should mean "a previously active concern is fading away" — it is a decay state generated when a ticker had prior events but has *zero* new events today. An event that reappears after a gap is REVERSING or CONFIRMING, not FADING. RESOLVED has the same problem. Additionally, media reuse of the same underlying story inflates occurrence counts — a one-time event covered by 10 outlets over 5 days looks like an ACCELERATING trend.

## Proposed approach

- In `compute_trend()`, move the opposite-direction check (→ REVERSING) to run *before* the `n30 == 0` guard (→ NEW). Order: REVERSING → NEW → ACCELERATING → CONFIRMING → fading range logic.
- FADING and RESOLVED are generated by a separate nightly sweep over tickers that had active events in the prior 30d but produced zero events today — they are not possible outcomes of `compute_trend()` for an event that is currently being observed.
- Introduce `event_fingerprint` (causal_key): a short hash of (ticker, event_type, direction, affected_metric) or the LLM-supplied `causal_key` string. Occurrence counts at 7/30/90d are computed over distinct `event_fingerprints`, not raw row counts. This prevents one multi-outlet story from looking like an accumulating trend.
