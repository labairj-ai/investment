# TODO 0823 — Build an Owner-Authorized OptiPlex Deployment Agent

- **ID:** 0823
- **Status:** backlog
- **Priority:** critical strategic
- **Risk:** L5 — production deployment
- **Depends:** 0816, 0817, 0819
- **Blocks:** 0824

## Problem

The current workflow can merge through GitHub but ChatGPT has no direct SSH/Tailscale execution path to OptiPlex.

Deployment remains an external manual step.

To achieve the desired OK/NO workflow, deployment must become a separate, tightly constrained mechanism that accepts only an explicitly owner-approved merged `main` SHA.

## Architecture

The deployment component must be separate from:

- Scout
- Planner
- Builder
- Reviewer

It must never execute arbitrary instructions generated by those agents.

Preferred implementation: tightly scoped self-hosted GitHub Actions runner or equivalent fixed deployment service on OptiPlex.

## Scope and acceptance

### Admission

Deployment requires:

- [ ] exact merge SHA exists on `main`;
- [ ] exact merge contains approved PR head;
- [ ] fresh owner approval exists;
- [ ] exact-head CI is green;
- [ ] required domain gates are green;
- [ ] deployment authorization explicitly covers the merge;
- [ ] no emergency stop is active.

### Preflight

- [ ] Verify current deployed SHA.
- [ ] Verify Git working tree.
- [ ] Refuse unexpected tracked-file modifications.
- [ ] Record untracked runtime overlays separately.
- [ ] Verify service configuration.
- [ ] Verify available disk space.
- [ ] Verify current service health.
- [ ] Create approved production backup.
- [ ] Verify backup integrity.
- [ ] Record holdings hash.
- [ ] Record development-ledger hash where appropriate.
- [ ] Create rollback target.

### Deployment

- [ ] Fetch reviewed repository.
- [ ] Check out exact approved merged SHA.
- [ ] Never deploy a PR branch SHA as final production state.
- [ ] Install/update only explicitly reviewed service/unit files.
- [ ] Restart `investment.service`.
- [ ] Reload systemd only when required.
- [ ] Start/restart affected timers only when explicitly included.

### Verification

- [ ] `investment.service` active.
- [ ] deployed Git SHA exactly matches target.
- [ ] tracked production files match HEAD.
- [ ] dashboard returns expected HTTP status.
- [ ] authenticated API works.
- [ ] unauthorized protected API access is denied.
- [ ] read-only Advisor health passes.
- [ ] Advisor functional canary passes.
- [ ] mutation-safety canary passes.
- [ ] holdings hash unchanged unless the release explicitly authorizes state change.
- [ ] development ledger contains only expected records.
- [ ] auto-merge remains disabled.
- [ ] autonomous implementation policy remains unchanged unless separately approved.

### Rollback

On failed verification:

- [ ] immediately stop promotion;
- [ ] restore prior code/config release;
- [ ] restart service;
- [ ] rerun health checks;
- [ ] never overwrite production investment data as part of code rollback;
- [ ] preserve failed deployment evidence.

## Durable deployment receipt

Record:

- authorization ID
- PR number(s)
- PR head SHA
- merge SHA
- deployed SHA
- prior SHA
- timestamp
- CI run
- release gates
- backup receipt/hash
- holdings hash before/after
- service state before/after
- dashboard health
- API health
- canary outcomes
- deployment actor/service identity
- rollback target
- final status:
  - `DEPLOYED_VERIFIED`
  - `DEPLOYED_DEGRADED`
  - `ROLLED_BACK`
  - `FAILED_PRECHECK`

## Security requirements

- [ ] Runner cannot push code.
- [ ] Runner cannot approve PRs.
- [ ] Runner cannot modify GitHub rulesets.
- [ ] Runner cannot create owner approvals.
- [ ] Builder cannot invoke arbitrary commands on runner.
- [ ] Deployment command set is static and versioned.
- [ ] No generic remote shell endpoint.
- [ ] No arbitrary user-supplied shell strings.
- [ ] Secrets remain on deployment host.
- [ ] Production database never enters model context.

## QA requirements

Test:

- successful deployment;
- bad SHA;
- stale owner approval;
- failed CI;
- dirty tracked worktree;
- service restart failure;
- dashboard failure;
- Advisor canary failure;
- holdings mutation;
- rollback;
- interrupted deployment;
- repeated/idempotent deployment of same SHA.

## Done when

- [ ] A merged owner-approved low-risk PR can deploy to OptiPlex without manual SSH.
- [ ] Deployment produces durable evidence automatically.
- [ ] Failed canary automatically prevents successful deployment status.
- [ ] Owner interaction remains OK/NO only.
