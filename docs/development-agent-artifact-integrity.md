# Authoritative validation-result boundary

Candidate code and pytest sharing a Python interpreter cannot supply independent PASS evidence, even if a host process later serializes JUnit. Python can monkeypatch pytest hooks or forge its output. A pipe, read-only oracle files, expected inventory, HMAC key embedded in that interpreter, or host-side parsing alone does not solve this.

`result_collector.py` normalizes bounded diagnostic output and exclusively writes immutable host-private final receipts. Candidate XML, stdout and process exit cannot grant PASS. An independent oracle adapter must execute the approved behavioral checks in a separate process that never imports candidate Python; candidate application behavior must cross an explicit constrained interface. The adapter attests every expected test identity/result, exact candidate/base/source/oracle/image binding and isolation protocol using an operator-controlled key that never enters candidate mounts. Host normalization verifies the authenticated receipt. Missing adapter returns UNAVAILABLE and blocks technical certification/autonomy.

Existing general pytest unit tests remain repository diagnostics. They are not silently promoted to the independent protocol. Supporting their arbitrary in-process imports as a hostile-code oracle requires a new isolated application/test interface, not a file-ownership change. This is a real acceptance dependency: fixture signatures prove protocol handling, not deployed oracle isolation. Until an approved adapter and runtime pass the 0818 live attacks, 0818 is incomplete, technical certification remains unavailable, and 0822/0824 autonomous progression is blocked.

No candidate receives a mount of the host's final collector directory or signing key. Keep raw diagnostic artifacts separate from normalized authoritative receipts, bounded and non-executable; never consume candidate PASS JSON as an attestation. Preserve networklessness, read-only source, no credentials/socket/capabilities and the approved-base test tree.
