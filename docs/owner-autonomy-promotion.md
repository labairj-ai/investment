# Owner autonomy promotion contract (interface only)

`OWNER-AUTONOMY-PROMOTION autonomy-promotion-1` is a future owner-authenticated authorization distinct from PR review, build policy and a promotion recommendation. Required binding: repository, structural harness SHA256, activation PR number, exact activation head SHA, requested stage, L2 maximum risk, bounded daily cap, verified owner login and numeric ID, timestamp, single-use nonce and rationale. The decision must follow a qualifying evidence report and must be reverified on current GitHub APIs. New harness, head, policy, owner identity or stage invalidates the binding. A stale approval cannot authorize activation. Revocation and replay rejection are mandatory.

This PR supplies `owner_promotion.validate_binding()` as a shape/context contract only. A successful binding check explicitly reports `authenticated=false` and grants no authority. `owner_promotion.authorization()` always returns UNAVAILABLE because no owner-authenticated issuer/ingestion/verifier has been implemented. There is no dashboard, CLI, model, environment or config route that creates accepted promotion authority. Generic ledger insertion of OWNER_AUTONOMY_PROMOTION is reserved and rejected. Even direct operator-written ledger JSON cannot activate the unavailable adapter.

Runtime requires both the shared qualifying safety evidence and this separate owner authorization. Therefore a config flip alone cannot enable autonomous starts, including after all technical evidence passes. A future separately reviewed L5 change must implement and test the actual authenticated owner channel, current activation-PR binding, nonce consumption, revocation and audit lineage before this adapter can return PASS. No token or credential belongs in an authorization payload.

Promotion preparation additionally requires autonomy to remain disabled. That reporting precondition is intentionally separate from shared read-only safety qualification, which is evaluated unchanged before and after a config flip. Runtime retains stage ordering and its stricter owner-authorization requirement. Neither report grants merge or deployment authority.
